This is a Roblox bootstrapper that runs the macOS client on Linux. The UI toolkit used is iced.

There are some things to know before making changes:

- MOST IMPORTANT: Make the code as self explanatory as possible, no comments.
- The UI follows iced's model: views are functions of `AppState` and page/component state that return `Element<Message>`, and changes happen in `update`. Views must stay cheap and side-effect free: never touch the filesystem or network from a view, cache such results in the page's state and refresh them from `update`.
- `quadra::act` turns a change to `AppState` (or a backend call) into a `Message`. Reactions to state changes that need the window, such as opening a dialog, go through the reactions queue in `src/quadra.rs`.
- Keep the widget tree shape stable around stateful widgets like text inputs: reserve space for optional elements instead of inserting them, or the widget loses its focus.
- The glib main loop is replaced by `src/main_loop.rs`, which runs futures and timers on the UI thread and is woken by iced. Use it instead of spawning work on the UI thread any other way.
- When making a new component, add it in `src/components/**` and export them. Shared look and widget styles live in `src/components/style.rs`, rows and groups in `src/components/preferences.rs`.
- A theme is a `Look` in `src/components/style.rs` plus an optional backdrop. Still backdrops must cost nothing per frame once drawn: use a gradient, a canvas `Cache`, or a GPU primitive like the line field, and never send a new image to the renderer every frame.
- Animated backdrops are scenes in `src/components/scene_backdrop.rs`, with their WGSL in `src/components/scenes/`. A scene draws on the GPU and schedules its own frames with redraw requests instead of messages, so `update` and `view` don't run per frame. Keep scenes at a capped frame rate, paint expensive light into the low resolution glow texture, draw small moving things as motes, and let the clock settle them when the window loses focus or gets no input for a minute. Wrap every scene in `gpu_or` with a still backdrop for the software renderer. Scenes take their colours from a `Palette`: the window colour plus up to three lights, read in WGSL through `scene.base` and `tint()`, so a new scene must look right on light and dark windows. Gallery previews always show a theme's own scene and colours, never the Background animation setting.
- Effects that follow the pointer, like the cursor effects in `src/components/cursor_effect.rs` and the Grid bulge in `src/components/grid_bulge.rs`, draw at the pointer's latest position on every move instead of easing towards it, and only fade their strength.
- Every animation follows `AppState::motion()`: the Animations setting, lowered to Reduced when the desktop asks for less motion. Reduced slows scenes and draws the line field at once, Off shows still backdrops. Layers drawn behind the whole window go in one `flat_stack`, because each extra layer redraws the whole window on software renderers. Anything that animates must ask for frames only while it is actually changing.
- Settings search works through `preferences::searching`: rows and groups hide themselves when they don't match, so build settings out of `preference_row` and `preference_group`, and wrap anything else in `searchable` with the words people would search for.
- `src/components/theme_backdrop.rs` decides each window's backdrop from the theme, an imported CSS theme and the Background animation setting. Imported themes are parsed in `src/components/imported_theme.rs` and loaded from disk in `src/backend/themes.rs`; document new theme properties in the README.
- When making a new page, give it its own folder `src/pages/<name>/` and export it in `src/pages.rs`. The page itself goes in `mod.rs`, and functions that only that page uses go in separate files inside the same folder.
- Utility functions go to `src/utils.rs`.
- Backend code (installing, downloading, running Rosemary and Roblox) goes in `src/backend/`, with its public actions in `src/backend.rs`. It talks to the UI only through `AppState`; long work runs in the background with `run_task` (user-started work: marks Quadra busy, shows progress, failures open an error dialog) or `run_quietly` (fetches the user shouldn't notice: nothing is blocked, the caller handles the `Result`, usually by logging it).
- When making changes to the UI that need new state properties, you may modify in `src/state.rs` and use the abstractions in your changes, otherwise when state is needed but only existing ones, then still use the abstractions.
